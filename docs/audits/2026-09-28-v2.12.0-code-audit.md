## Security

### S1 · High · CIDR filter mode takes the leftmost X-Forwarded-For entry as the client IP

`lib/otto/utils.rb:253` · ip-spoofing / broken-trust-boundary · **Consensus 3/3** · also C1

**Why it matters.**

*The mechanism.*
- `Otto::Utils.resolve_client_ip` is the single resolver behind `IPPrivacyMiddleware` and `Otto::Request#client_ipaddress`.
- In filter mode it concatenates `HTTP_X_FORWARDED_FOR`, `HTTP_X_REAL_IP` and `HTTP_X_CLIENT_IP`, then returns the first entry that is not a trusted proxy (lines 249-259).
- Common reverse proxies append the observed peer to the inbound header instead of replacing it. This includes nginx `$proxy_add_x_forwarded_for`, ALB, Cloudflare and Caddy. So the leftmost entry is whatever the client sent.
- Depth mode in the same file already handles this; the comment at line 273 reads "a forged leftmost entry is never reached". `Rack::Request#ip` also takes the last untrusted entry. Filter mode does the opposite.

*Reproduced through the full stack.*
- Setup: `trusted_proxies: ['10.0.0.0/8']`, `REMOTE_ADDR=10.0.0.5`, `X-Forwarded-For: 1.2.3.4, 203.0.113.9`.
- Result: `env['otto.client_ip']` is `1.2.3.0`.
- `env['otto.ip_match'].call(['1.2.3.0/24'])` returns `true`, but the real peer's range `203.0.113.0/24` returns `false`.
- The same happens when nginx sets `X-Real-IP` correctly but passes the client's `X-Forwarded-For` through, because XFF is read first.

*Impact.*
- `docs/guides/privacy.md:147-148` points to `env['otto.ip_match']` "For precise access control without exposing the address to application code". That check can be bypassed.
- The following all key on an address the attacker chooses:
  - `req.ip` and `otto.client_ip`, which feed rate-limit keys when Rack::Attack runs inside Otto, audit logs, and RouteAuthWrapper metadata
  - `correlation_hash` and `hashed_ip`
  - the geo lookup
  - `Request#local?`
- The spec at `spec/otto/utils_spec.rb:454`, titled "walks the forwarded chain and returns the first non-proxy address", pins the current behavior.

**Suggested fix.**
1. Walk the chain from the right:
   - Build it per header instead of concatenating three headers, and reverse it.
   - Skip entries where `security_config.trusted_proxy?` is true, and return the first untrusted one. This matches `resolve_client_ip_by_depth` and `Rack::Request#ip`.
   - Fall back to `REMOTE_ADDR` when every entry is trusted.
2. Read the single-valued `X-Real-IP` / `X-Client-IP` only when `X-Forwarded-For` is absent, or prefer them when the proxy sets them. Never treat them as extra chain positions.
3. Update the spec at `utils_spec.rb:454` to assert the rightmost untrusted entry.
4. Add a padding test that mirrors the depth-mode one: `9.9.9.9, 203.0.113.50` must resolve to `203.0.113.50`.
5. State in `docs/guides/forwarded-authority.md` that proxies must append to the header, not pass it through.

### S2 · High · `Config#deep_freeze!` is not idempotent, so MCP auth tokens make every request fail after the first

`lib/otto/security/config.rb:1216` · denial-of-service / security-feature regression · **Consensus 3/3**

**Why it matters.**

*The mechanism.*
- `Otto::Core::Freezable#deep_freeze!` returns early when the object is already frozen.
- `Otto::Security::Config#deep_freeze!` overrides it. It runs three validators before calling `super` (lines 1215-1218): `validate_referrer_policy!`, `validate_trusted_proxy_config!` and `validate_csrf_secret_config!`.
- `validate_trusted_proxy_config!` ends in `commit_rack_forwarding_family!`, whose first statement is `ensure_not_frozen!` (line 722).
- `Otto#freeze_configuration!` freezes `@security_config` first and then deep-freezes the middleware stack, which walks each entry's args.
- `Otto::MCP::Server` passes the security config as a middleware argument in two places:
  - `TokenMiddleware` (`lib/otto/mcp/server.rb:169`)
  - `RateLimitMiddleware` (`:176`, on by default)
- So the already-frozen Config is visited a second time, and it raises `FrozenError` ("Cannot modify frozen configuration").
- The raise happens in `Otto#call` outside the rescue that feeds `handle_error`. `@configuration_frozen` is never set, so every later request retries the freeze and fails the same way.

*Reproduced outside RSpec.*
- This call raises: `Otto.new(routes, mcp_enabled: true, mcp_http: true, mcp_auth_tokens: ['tok'], mcp_rate_limiting: false, mcp_validation: false).call(env)`.
- The same app with `mcp_allow_unauthenticated: true` returns 200.
- The rate-limiting path was confirmed by reading only, because rack-attack is not installed here.

*Why tests miss it.* `Otto#call` skips the lazy freeze under RSpec, and the MCP specs use `Otto.unfreeze_for_testing`.

*Impact.* The token setup shown in `docs/guides/mcp.md:52` (`mcp_auth_tokens: [ENV.fetch('MCP_TOKEN')]`) takes down the whole application in production. That pushes operators toward `allow_unauthenticated: true`.

**Suggested fix.**
1. Add `return self if frozen?` as the first line of `Config#deep_freeze!`, matching `Freezable`.
2. Make `commit_rack_forwarding_family!` tolerate re-entry: return early when this config already committed the family, instead of calling `ensure_not_frozen!` unconditionally.
3. Preferably, stop passing the Config as a middleware argument. Add `TokenMiddleware` and the MCP `RateLimitMiddleware` to `MiddlewareStack#middleware_needs_config?` so `#wrap` injects the config.
4. Add a regression spec: build an Otto with `mcp_auth_tokens`, call `freeze_configuration!` explicitly, then serve a request through `#call`.

### S3 · Low · A non-String `_csrf_token` parameter turns a CSRF rejection into a 500

`lib/otto/security/csrf_validation.rb:40` · input-validation / error-handling · **Consensus 3/3** · also C11

**Why it matters.**
- `valid_csrf_token?` reads the token from `request.params` and calls `token.strip`.
- Rack parses `_csrf_token[]=abc` into an Array and `_csrf_token[a]=b` into a Hash, so `.strip` raises `NoMethodError`. The error reaches `handle_error` as unhandled.
- Reproduced: `POST /form?_csrf_token[]=abc` with CSRF enabled returns 500 and logs "Unhandled error in request" with a backtrace. A String token gets the intended 403.
- `Config#verify_csrf_token` makes the same assumption (`.split`).
- There is no bypass. But any client can produce ERROR-level logs with backtraces that count as server faults against error budgets and alerting.

**Suggested fix.**
- In `valid_csrf_token?`: `return false unless token.is_a?(String) && !token.strip.empty?`
- At the top of `Config#verify_csrf_token`: `return false unless token.is_a?(String)`
- Add specs for Array and Hash token params that expect 403.

### S4 · Low · MCP bearer-token comparison leaks configured token lengths through timing

`lib/otto/mcp/auth/token.rb:34` · timing-side-channel · **Consensus 2/3**

**Why it matters.**
- `TokenAuth#valid_token?` compares the raw candidate against each configured token with `Rack::Utils.secure_compare`. That function returns immediately when the byte sizes differ.
- Response timing therefore shows whether the presented token's length matches a configured token, which narrows a brute-force search.
- The sibling `APIKeyStrategy` (`lib/otto/security/authentication/strategies/api_key_strategy.rb:192-198`) reduces both sides to SHA-256 digests to avoid exactly this. The two authenticators are inconsistent.

**Suggested fix.**
- Precompute `Digest::SHA256.hexdigest` for each configured token at construction.
- Compare with `Rack::Utils.secure_compare(token_digest, Digest::SHA256.hexdigest(candidate))`.
- Reject non-String configured tokens at construction, so a YAML integer cannot raise `NoMethodError` at request time.

## Correctness

### C1 · Critical · Client-IP resolution returns the leftmost, client-controlled X-Forwarded-For entry

`lib/otto/utils.rb:253` · ip-spoofing · **Consensus 3/3** · same issue as S1; the mechanism and fix are there

**What this finding adds.**
- A second reproduction: `REMOTE_ADDR=10.0.0.1` (with `10.0.0.0/8` trusted) and `X-Forwarded-For: 203.0.113.99, 198.51.100.7`.
  - Otto resolves `203.0.113.99`. `Rack::Request#ip` with the same trust settings resolves `198.51.100.7`, because Rack walks the list with `reverse_each`.
  - `env['otto.ip_match'].call(['203.0.113.99/32'])` returns `true`. An attacker passes an IP allowlist by naming an allowlisted address in XFF.
- `X-Real-IP` and `X-Client-IP` are appended to the chain. When XFF is absent and the proxy does not overwrite those headers, a client-supplied `X-Real-IP` wins.
- The existing spec at `spec/otto/utils_spec.rb:454` only uses a chain whose other entries are all trusted, so it cannot tell the two directions apart.

**Suggested fix.**
- Use `forwarded_ips.reverse_each { |c| ip = normalize_ip(c.strip); next unless ip; return ip unless security_config.trusted_proxy?(ip) }`, then fall back to `remote_addr`.
- Consult `X-Real-IP` / `X-Client-IP` only when XFF is absent.
- Add a spec with two untrusted entries (`spoofed, real`) that asserts the rightmost one wins. Mirror the depth-mode forged-leftmost test for filter mode.

### C2 · High · HEAD dispatch mutates the shared route tables

`lib/otto/core/router.rb:121` · correctness · **Consensus 3/3**

**Why it matters.**

*The mechanism.*
- Two lines mutate the registered tables whenever a HEAD route exists:
  - `literal_routes.merge! routes_literal[:GET] if http_verb == :HEAD` (line 121) changes `routes_literal[:HEAD]`.
  - `valid_routes.push(*routes[:GET]) if http_verb == :HEAD` (line 255) changes `routes[:HEAD]`.
- The `|| {}` / `|| []` fallback allocates a fresh container only when no HEAD routes exist.

*When the configuration is frozen* (the first request outside RSpec; `configuration.rb:309-310`):
- Every HEAD request raises `FrozenError` and returns 500.
- Reproduced with a routes file containing `HEAD /health`: after the first request, HEAD requests to `/health`, `/show/1` and `/other` all return 500.

*When it is not frozen* (under RSpec):
- `merge!` lets the GET entry win, so `HEAD /health` runs the GET handler instead of the declared HEAD handler.
- `@routes[:HEAD]` grew from 2 to 8 entries after three HEAD requests. That is unbounded growth of shared state, written from request threads without synchronization.

**Suggested fix.**
- Never mutate the registered tables at dispatch time. Build per-request views where the verb-specific entry wins:
  - `literal_routes = http_verb == :HEAD ? (routes_literal[:GET] || {}).merge(routes_literal[:HEAD] || {}) : (routes_literal[http_verb] || {})`
  - `valid_routes = http_verb == :HEAD ? (routes[:HEAD] || []) + (routes[:GET] || []) : (routes[http_verb] || [])`
- Better: compute the merged HEAD tables once, at load or freeze time.
- Add a spec that freezes the configuration, defines a HEAD route and issues HEAD requests.

### C3 · High · `warn_generated_csrf_secret` writes to the frozen config, so every HTML response returns 500

`lib/otto/security/config.rb:1349` · correctness · **Consensus 3/3**

**Why it matters.**
- `Config#deep_freeze!` freezes the instance on the first request outside RSpec.
- `generate_csrf_token` (line 795) then calls `warn_generated_csrf_secret`, which sets `@csrf_secret_warning_emitted = true` on the frozen object and raises `FrozenError`.
- Reproduced with `Otto.new` + `enable_csrf_protection!` and no `OTTO_CSRF_SECRET` or `csrf_secret=`, with `RACK_ENV` unset, `development` or `staging`:
  - Every GET of an HTML page returns 500, starting with the first request.
  - The failure path is `CSRFMiddleware#inject_csrf_token` → `generate_csrf_token` → `FrozenError`.
- The `production_environment?` guard does not help, because the failure is in the non-production branch.
- The similar `@csp_script_src_override_warned = true` is safe only because its callers are setters guarded by `ensure_not_frozen!`.

**Suggested fix.** Keep the once-only flag off the frozen instance. Any of these works:
- Emit the warning once at enable or freeze time, for example in `validate_csrf_secret_config!` or `enable_csrf_protection!`.
- Store the flag in a class-level `Concurrent::Map` keyed by `object_id`. `Otto::Privacy::Config` uses this pattern for rotation keys.
- Use a `Concurrent::AtomicBoolean` created in `initialize`.

Add a spec that calls `deep_freeze!` and then `generate_csrf_token` with a generated secret.

### C4 · High · `handle_auth_success` replaces the real Rack session with `{}` on noauth and role/permission routes

`lib/otto/security/authentication/route_auth_wrapper.rb:214` · correctness · **Consensus 3/3**

**Why it matters.**
- Line 214 is `env['rack.session'] = result.session if result.is_a?(StrategyResult) && result.session`. It treats any truthy session as authoritative.
- Two constructors default to `session: {}`, which is truthy:
  - `StrategyResult.anonymous` (`strategy_result.rb:115`)
  - `AuthStrategy#success` (`auth_strategy.rb:30`)
- Three strategies never pass the real session:
  - `NoAuthStrategy`
  - `RoleStrategy` (`role_strategy.rb:33`, `:41`)
  - `PermissionStrategy` (`permission_strategy.rb:33`)
- So on these routes the handler gets a bare Hash instead of the session middleware's `SessionHash`:
  - `auth=noauth`
  - an `auth=session,noauth` fall-through
  - role and permission routes
- Reproduced with rack-session 2.1.2 (`Rack::Session::Pool`):
  - `/plain` works.
  - `/noauth` and `/either` raise `NoMethodError: undefined method 'options' for an instance of Hash` from rack-session's `commit_session`.
- That error happens above Otto, so `handle_error` never sees it, and every session write the handler made is lost.

**Suggested fix.**
- Sync the session only when the strategy actually produced one, for example `env['rack.session'] = session if session && !session.empty? && !env.key?('rack.session')`.
- Cleaner: never overwrite an existing `env['rack.session']`, and have `StrategyResult.anonymous` / `AuthStrategy#success` default `session:` to `env['rack.session']`.
- Add an integration spec with rack-session that covers `auth=noauth` and role-strategy routes.

### C5 · High · CSRF session binding changes between GET and POST, so a new visitor's first form POST gets 403

`lib/otto/security/config.rb:1269` · correctness · **Consensus 3/3**

**Why it matters.**

*The mechanism.* `extract_existing_session_id` returns `session.id` first (line 1269) and checks `session[csrf_session_key]` only after that.

*The failing sequence for a new visitor.*
1. On the GET, rack-session's `SessionHash#id` is nil because the session has not loaded yet.
2. Otto generates a random hex id and stores it in `session['_csrf_session_id']`.
3. That write loads the session and makes rack-session mint a real SID.
4. The token is bound to the hex id.
5. On the following POST the session cookie exists, so `session.id` returns the rack-session SID.
6. The token is checked against a different binding and fails.

*Reproduced* with rack-session 2.1.2 for both `Rack::Session::Pool` and `Rack::Session::Cookie`:
- `GET /form` returns 200 and issues the token and the `_otto_session` cookie.
- `POST /submit` with that token and those cookies returns 403.

*Why it hides.* If the GET handler writes to the session first, the flow succeeds. Apps whose pages already touch the session never see the bug. It breaks the common login form that leaves the session untouched.

**Suggested fix.**
- Read `session[csrf_session_key]` before `session.id`. This also forces rack-session to load and assign its id.
- Always coerce `session.id.to_s`. rack-session returns a `SessionId` object. That is also why `ensure_session_cookie`'s `existing_cookie == session_id` never matches, so the cookie is set again on every response.
- Add an integration spec with rack-session: GET an HTML page without touching the session, then POST with the issued token.

### C6 · High · `csrf_secret=` accepts `''` and `nil`, defeating the production guard; empty-key tokens are forgeable

`lib/otto/security/config.rb:780` · security · **Consensus 3/3** · also T1

**Why it matters.**
- The initializer treats a blank `OTTO_CSRF_SECRET` as generated: `@csrf_secret_generated = configured_secret.nil? || configured_secret.empty?` (line 439).
- The setter (lines 780-785) stores any value and sets `@csrf_secret_generated = false` without checking it.
- Common idioms pass `''`: `config.csrf_secret = ENV.fetch('OTTO_CSRF_SECRET', '')` or `ENV['OTTO_CSRF_SECRET'].to_s`.
- Reproduced with `RACK_ENV=production` and `csrf_secret = ''`:
  - `generate_csrf_token` does not raise.
  - A token forged as `"deadbeef:#{OpenSSL::HMAC.hexdigest('SHA256', '', 'sess1:deadbeef')}"` verifies as valid. Anyone can mint CSRF tokens.
- With `nil`, the failure is loud but in the wrong place: `sign_csrf_token` raises `TypeError` on every HTML response (500) instead of a configuration error at boot.

**Suggested fix.**
- In the setter, raise `ArgumentError` unless `secret.is_a?(String) && !secret.strip.empty?`. Alternatively, treat a blank value as generated, exactly as the initializer does.
- Consider a minimum length.
- Add specs for `csrf_secret = ''` and `csrf_secret = nil`.

### C7 · Medium · `normalize_path` uses form decoding, so `+` becomes a space in every dispatch stage

`lib/otto/utils.rb:133` · correctness · **Consensus 3/3** · also T5

**Why it matters.**
- In Rack 3.2, `Rack::Utils.unescape` is `URI.decode_www_form_component`, which is the query and form decoder. The path decoder is `Rack::Utils.unescape_path`.
- Every dispatch stage sees `+` as a space: the literal table, the dynamic matcher, static mounts, the public dir, LocalhostGuard, the MCP endpoint and the CSP report path.
- Reproduced:
  - `normalize_path('/a+b')` returns `"/a b"`.
  - A literal route `GET /a+b` returns 404, while `/a%2Bb` matches. The literal table key at `router.rb:43` is the raw route path.
  - The public file `c++.txt` returns 404 at `/c++.txt` but is served at `/c%2B%2B.txt`.
  - A request for the non-existent `/a+b.txt` serves a different file, `a b.txt`.
- Browsers send `+` literally in paths, so every route or asset with a plus sign is affected.

**Suggested fix.**
- Use `Rack::Utils.unescape_path(raw)`. It raises the same ArgumentError family on malformed escapes, so the existing rescue stays valid.
- Normalize the literal-table keys with the same function at load time. `router.rb:43` currently only strips a trailing slash.
- Add specs for `+` in routes and in static file names.

### C8 · Medium · CSRF token injection replaces the response body without closing the original

`lib/otto/security/middleware/csrf_middleware.rb:67` · resource-leak · **Consensus 3/3**

**Why it matters.**
- `inject_csrf_token` reads the downstream body with `body.join` (line 56) and returns `[status, headers, [body_content]]` (line 67). The original body object is dropped.
- Rack requires the server to call `close` on the body it receives. The server now sees only the new Array.
- So a downstream `Rack::BodyProxy` never runs its close block. Affected users include Rack::Lock, Rack::ETag, rack-timeout, ActiveRecord/Sequel connection release, and wrapped file bodies.
- Reproduced: an app returning `Rack::BodyProxy.new(['<html><head></head></html>']) { closed = true }` still has `closed == false` after the returned body is fully consumed and closed.
- Under Rack::Lock this leaves the mutex held.

**Suggested fix.**
- Close the original body before returning the new triple: `body.close if body.respond_to?(:close)`. Alternatively, return `Rack::BodyProxy.new([body_content]) { body.close if body.respond_to?(:close) }`.
- Iterate with `each` instead of relying on `join`, so non-Array bodies are handled the same way.

### C9 · Medium · Non-object JSON-RPC payloads and params raise instead of returning -32600 / -32602

`lib/otto/mcp/protocol.rb:70` · error-handling · **Consensus 3/3** · also T2

**Why it matters.**
- `valid_jsonrpc_request?` correctly returns false for a non-Hash payload. But the failure branch at line 70 immediately evaluates `data['id']`:
  - Array and Integer payloads raise `TypeError`.
  - `nil` and `true` raise `NoMethodError`.
- `params` has the same problem at line 124 (`params['uri']`) and line 151 (`params['name']`) when it is an Array or Integer.
- These inputs all raise out of `Protocol#handle_request`:
  - bodies `[]`, `null`, `123` and `true`
  - a `resources/read` request with `"params":[1]` or `"params":5`

**Suggested fix.**

### C10 · Medium · Logic-class JSON parsing calls `rack.input#size` and `#rewind`, so JSON POSTs fail under Rack::Lint

`lib/otto/route_handlers/logic_class.rb:128` · compatibility · **Consensus 3/3** · also T3

**Why it matters.**
- `json_body?` calls `req.body&.size&.positive?` (line 128), and `parse_json_body` calls `req.body.rewind` (line 137).
- Rack 3 dropped the rewind requirement for `rack.input` and never required `#size`. Rack::Lint's `InputWrapper` exposes only `gets`, `read`, `each` and `close`.
- Reproduced: `POST /echo` with `{"name":"zed"}` to a `response=json` Logic route:
  - returns 200 when calling Otto directly
  - returns 500 under `Rack::Lint.new(otto)`, with `NoMethodError: undefined method 'size' for an instance of Rack::Lint::Wrapper::InputWrapper`
- Any SPEC-conformant server with a streaming, non-rewindable input hits the same path.

**Suggested fix.**
- Decide whether there is a body from the request, not the IO: `req.content_length.to_i > 0 || env['HTTP_TRANSFER_ENCODING']`.
- Read once with `req.body.read`, and call `rewind` only if `req.body.respond_to?(:rewind)`.
- Cache the parsed JSON in `env` so later readers do not need the stream.
- Add a spec that runs the handler under Rack::Lint.

### D2 · Medium · `sanitize_params` writes its results to a throwaway Hash

`lib/otto/security/middleware/validation_middleware.rb:100` · dead-store · **Consensus 3/3**

**Why it matters.**
- In Rack 3, `Rack::Request#params` returns a new `GET.merge(POST)` Hash on every call.
- `validate_parameters` passes that temporary Hash to `sanitize_params`, which assigns `params[key] = sanitize_value(value)` and then drops it. It also visits only top-level values.

**Suggested fix.** Decide whether this middleware rejects or rewrites.
- **Reject only:** make `sanitize_value` a pure check (keep the raises, drop the Loofah/gsub output), and correct the comment and README.

### P1 · Low · The gem-publishing job installs 75 dev and optional gems while holding `id-token: write`
